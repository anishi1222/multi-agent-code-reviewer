# 0008: 制御の適用範囲は、その呼び出し箇所から見えなければならない

- Status: Accepted
- Date: 2026-08-06
- Deciders: Multi-Agent Code Reviewer maintainers
- Tags: architecture, enforcement, invariants, ports-and-adapters, testing

## Context

本再構築で報告された欠陥のうち、**10 件が同一の形**をしています。個別には無関係に見え、
別々のタスクで別々の担当者が発見しましたが、根は 1 つです。

> ある制御（上限・検証・ゲート・アーキテクチャルール）が存在するかどうか、
> そして**どこまでに効くのか**が、その制御の呼び出し箇所からは分からない。

読者はコードを読んで「この値は検証済みだ」と考えます。実際には検証器は死んでいるか、
別の量を見ているか、そもそも判断に必要な入力を受け取れていません。
**症状ではなく、この形そのもの**を本 ADR の対象とします。

### 観測された 10 件

| # | 出所 | 形 | 何が見えなかったか |
|---|---|---|---|
| 1 | t12 | 空虚な制御 | ルールは存在するが対象集合が空で、無条件に成功していた |
| 2 | t13.1 / G1 | 空虚な制御 | 同上 |
| 3 | t16 | 空虚な制御 | 同上 |
| 4 | t18 / SEC-H1 | 宣言のみの制御 | `ALLOWED_CHAR_RANGE` が定義されているが、どこからも適用されていない |

10 件目は本 ADR の作成中に見つかったもので、最も重い証拠です。詳細は
[Finding: ADR-0007 D5 は履行されていない](#finding-adr-0007-d5-is-unfulfilled) を参照。

### なぜ「注意して書く」では解けないか

1〜10 はいずれも、書いた人間が不注意だったから起きたのではありません。
**呼び出し箇所に情報が無い**以上、読者はそれを知りようがないからです。
規約やレビューでは、読者が「見えないもの」を見落とす確率を下げられません。
したがって本 ADR の決定は、すべて**機械化された形**を持たなければなりません。

これは ADR-0006 D5 の要求そのものです。

> 許可インポート表の行に対応する強制ルールが存在しないことは、それ自体が欠陥である。

## Decision

### D1. `domain` は設定既定値を直接読まない

`domain` 配下のクラスは `shared.ConfigDefaults` を参照してはなりません。
実効値は**純粋値として内側へ注入**します（`shared.PromptBudget` / `shared.SkillBudget`）。

F4 はこの規律の欠如そのものでした。同じ「スキルパラメータ長」という 1 資源に対し、
2 箇所のゲートが**異なる出所の異なる量**を見ていました。

| ゲート | 読んでいた量 | 失敗時の挙動 |
|---|---|---|
| 呼び出し前チェック | 設定値 `skill.max-parameter-value-length` | 警告してスキップ |
| 実行時チェック | `ConfigDefaults.SKILL_MAX_PARAMETER_VALUE_LENGTH`（定数） | 例外送出 |

どちらの呼び出し箇所にも「もう一方が存在する」ことも「両者が食い違い得る」ことも
書かれていません。設定を変更すると 2 つのゲートが**静かに乖離**します。

修正は「片方を直す」ではなく、**実効値の唯一の到達経路を注入に一本化する**ことでした。

### D2. 違反 0 件・例外 0 件のルールは、恒久的な否定的対照を持たなければならない

`LayerDependencyRulesTest` の例外方式（違反集合と例外集合の**完全一致**を主張する）は、
例外が 1 件でもあれば、そのルールが実際に発火することを毎回観測させます。
しかし**違反 0・例外 0 のルールでは、この機構は何も観測しません。**

Rule 8 はまさにその形です。述語が壊れていても、`CONFIG_DEFAULTS` の綴りが誤っていても、
そもそも参照が定数プールに現れなくても、**まったく同じ緑**になります。
これを対照なしで導入することは、本 ADR が禁じている形を、
**それを防ぐための機構の内部で**再現することに他なりません。

したがって Rule 8 は、恒久的な否定的対照テストと**同時にのみ**存在してよいものとします。

### D3. ルールの宣言範囲は、検査機構が実際に強制できる範囲と一致させる

Rule 8 は当初「`domain` は `ConfigDefaults` の**上限定数**を読まない」と記述されていました。
しかしこの粒度は**強制不可能**です。

`SKILL_MAX_PARAMETER_VALUE_LENGTH` は `public static final int`、すなわち
JLS §4.12.4 の *constant variable* です。JLS §13.1 によりコンパイル時に解決されるため、
読み出しは `sipush 10000` になり、**`Fieldref` は一切生成されません**。
バイトコード上にフィールド名は存在せず、フィールド単位の強制は「難しい」のではなく
「不可能」です。強制可能な単位は**型**です。

そこで**ルールの記述側を、強制可能な範囲へ狭めました**。Rule 8 は型 `ConfigDefaults` への
参照を全面的に禁じます。これは元の文よりも**広い**（純粋ヘルパー
`defaultIfBlank` / `defaultIfNonPositive` の呼び出しも禁じる）ため、その事実を
ルール本体のコメントに明記します。

> 表の行より**広い**ルールは、行が無いルールよりも危険である。
> 広げるなら、広げたことを書く。

現時点で違反は 0 件であり、この拡大に費用は発生していません。既定値の実体化は
`infrastructure.config` と `shared` の責務であり、両者のアクセスは維持されます。

### D4. 予算・上限は、純粋値オブジェクトとして内側へ注入する

`shared.PromptBudget` / `shared.SkillBudget` は本 ADR の**是正手段であって違反ではありません**。
`domain` がこれらに依存することは ADR-0006 Rule 1 が既に許可しています。
Rule 8 が予算値オブジェクトを検出した場合、**誤っているのはルールであって値オブジェクトではありません**。

F1（1 つのつまみが 3 つの予算に別名で効く）に対する是正も同じ形です。
つまみを増やすのではなく、**予算ごとに出自を持つ値**を与えます。

### D5. 完全性の表明は、独立した側を持たなければならない（既知の限界）

Rule 0 は「解析器がすべてのクラスを見た」ことを主張しますが、比較している 2 つの数
（`classFilesOnDisk` と `dependencies.size()`）は**いずれも同じ `target/classes` 走査に由来**します。
したがって Rule 0 が証明できるのは「**コンパイル済みのもの**を全部見た」ことだけで、
「**ソースにあるもの**を全部見た」ことは証明できません。

これは自己参照的な完全性表明であり、本 ADR の形の一種です。
現時点では機械化せず、**手順**として残します。大規模マージの後は、
ソース側から独立に数えた結果と `target/classes` を突き合わせること
（round-0 実績: ソース 175 ファイル ↔ `.class` 175）。

## Enforcement

**各決定は、対応する実在のテストを 1 つずつ持ちます**（ADR-0006 D5 の要件を本 ADR にも適用）。
**本 ADR は、履行されていない強制を表に書きません。** 10 件目の欠陥がまさにそれだったためです。

| 決定 | 強制手段 | 種別 | 否定的対照の形 |
|---|---|---|---|
| D1 | `LayerDependencyRulesTest` **Rule 8**: `domain` 配下 58 クラスが `shared.ConfigDefaults` を参照しないこと（例外 0 件・完全一致方式） | 構造 | F4 の原形を `domain` に戻すと即座に赤（実測済み。下記参照） |
| D2 | `LayerDependencyRulesTest` **Rule 8 control**: 定数のみを読むフィクスチャの定数プールに `shared.ConfigDefaults` が現れることを主張 | 否定的対照 | 検出が失われた瞬間に赤になり、「Rule 8 は盲目になった」と報告する |
| D3 | Rule 8 の述語が型一致（`dep.equals(CONFIG_DEFAULTS)`）であること、および拡大の明示がルール本体に存在すること | 規約 | — |
| D4 | Rule 1（`domain` 純粋性）が `shared` への依存を許可し続けること。Rule 8 は `ConfigDefaults` のみを禁じる | 構造 | 予算値オブジェクトを誤検出したらルール側の欠陥として扱う |
| D5 | — （**意図的に未機械化**。手順として運用） | 手順 | 大規模マージ後のソース↔クラス突き合わせ |

### 否定的対照の実測

D1 の対照は机上ではありません。F4 の原形を `domain.agent.AgentPromptBuilder` に
そのまま戻して実測しました。

```
[arch] Rule 8 (domain ⊥ shared.ConfigDefaults)  58 classes inspected, 1 violator(s), 0 exempt
  dev.logicojp.reviewer.domain.agent.AgentPromptBuilder
      -> dev.logicojp.reviewer.shared.ConfigDefaults
 ==> expected: <[]> but was: <[dev.logicojp.reviewer.domain.agent.AgentPromptBuilder]>
```

違反クラス名と禁止された辺の両方が出ます。その後リバートし、緑（0 違反）に戻ることを確認済み。

### Rule 8 が見えないもの（既知の穴）

JDK 28 で実測した結果、**`case` ラベル**で定数を読む形
（`case ConfigDefaults.SOME_MAX ->`）は、読み出し側の定数プールに**痕跡を一切残しません**。
Rule 8 はこの形を検出できません。

予算ゲートは比較（`>`）で書かれ `switch` では書かれないため、この穴は実務上到達しにくいと
判断し、**塞がずに記録**します。隠すよりも書いておくほうが、本 ADR の趣旨に適います。

なお Rule 8 が定数の読み出しを検出できるのは、javac が値をインライン化した後も
**参照されない `CONSTANT_Class` エントリ**としてコンパイル時依存を残すためです。
これは JVM 仕様の保証ではなく**コンパイラの挙動**です。D2 の対照テストは、
この前提が将来失われたときに赤くなるための装置です。

## Finding: ADR-0007 D5 is unfulfilled

本 ADR の作成中に、10 件目の実例が見つかりました。**未修正であり、本 ADR の範囲外です。**

ADR-0007 D5 は次を宣言しています。

> `application.port` 配下のクラスが `shared.SensitiveHeaderMasking` を参照しないことを
> **`LayerDependencyRulesTest` の Rule 4b** として追加

実測結果:

- `src/test` に **`Rule 4b` は存在しません**（文字列として 0 件）
- 一方 `application/port/outbound/McpServerSpec.java:34` は
  `SensitiveHeaderMasking.wrapHeaders(headers)` を**実際に呼んでいます**
  （バイトコードにも 4 箇所出現。javadoc 上の言及ではありません）

つまり **Accepted 状態の ADR が宣言した強制が実装されず、その違反が本番コードに生存しています。**
ADR-0006 D5 が「行を追加したら同じコミットで強制ルールを追加する」と定めた、まさにその欠陥です。

**本 ADR では修正しません。** Rule 4b を今追加すれば即座に赤くなり、
`McpServerSpec` を是正するか例外として正当化するかの設計判断が必要になります。
これは Rule 8 の導入とは独立した作業であり、同じ変更に束ねると
Rule 8 の緑が何を意味するのか説明できなくなります。別タスクとして起票します。

## Consequences

### 得られたもの

- F4 の再発は**ビルドで止まります**（Rule 8、否定的対照は実測済み）
- Rule 8 自身が空虚化した場合、それを**別のテストが報告します**（D2）
- 既定値の実効値は注入経路に一本化され、呼び出し箇所から**見える**ようになりました

### 支払った費用（明示）

**層構造は F4 の修正を簡単にせず、むしろ難しくしました。** これを書かない ADR は信用されません。

`AgentPromptBuilder` は `domain` にあるため、ADR-0006 Rule 1 により
`infrastructure.config.SkillConfig` をインポートできません。
「設定値をそのまま読めばよい」という最短の修正は、**層の規律によって塞がれていました**。
結果として F4 は 1 行の変更ではなく、`SkillBudget` という値をどこで組み立て、
どこから注入するかという**設計作業**になりました。

これは層構造が誤っていたことを意味しません。同じ規律が「domain が設定を読む」という
本来の誤りを防いだのですから、費用は規律の対価です。ただし
**「層に分けたので修正が楽になる」は、この件については成り立ちませんでした。**

### 残る限界

- Rule 8 は `case` ラベル経由の定数読み出しを検出できません（上記）
- Rule 8 の検出はコンパイラ挙動に依存します（D2 が監視）
- Rule 0 の完全性表明は依然として自己参照的です（D5、手順で補完）
- ADR-0007 D5 の Rule 4b は未実装のままです（別タスク）
